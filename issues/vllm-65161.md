# vLLM #65161 — EAGLE and CPU KV Offloading

**Issue:** https://github.com/vllm-project/vllm/issues/65161  
**Status of this investigation:** Understanding / current-main reproduction pending  
**Last reviewed:** 2026-11-04

## Reported problem

The reporter observed that with EAGLE speculative decoding and an OffloadingConnector CPU tier, a prefix-cache hit can cause the last EAGLE-dropped block to be loaded from CPU.

That load can be slower than simply recomputing the short tail on GPU.

The report describes a vLLM 0.32.0 setup with Qwen3-4B, an EAGLE-3 draft head, GPU/CPU KV tiers, and competing high- and lower-priority requests.

## Initial code-path map

1. `FullAttentionManager.find_longest_cache_hit` finds a local GPU prefix.
2. With legacy EAGLE block-drop behavior, the last matched cache unit may be excluded.
3. `Scheduler` asks the KV connector whether external cache can extend the hit.
4. `OffloadingConnectorScheduler` looks up the available CPU tier.
5. An async load may make the request wait in `WAITING_FOR_REMOTE_KVS`.
6. For a short suffix, scheduling and transfer cost may exceed GPU recomputation cost.

This is a **source-informed model of the reported behavior**, not a verified trace for the latest main.

## Important upstream changes

- **Merged 2026-10-26:** [#61589 — local lookahead block hashes](https://github.com/vllm-project/vllm/pull/61589).
- **Merged 2026-11-03:** [#64096 — lookahead hashes for compatible KV connectors](https://github.com/vllm-project/vllm/pull/64096).

The current `OffloadingConnector` declares support for lookahead block hashes. When enabled, lookahead proves the needed boundary and may remove the automatic EAGLE last-block drop.

**Do not assume this issue still reproduces on main.** Different connector combinations or explicit feature switches may behave differently.
