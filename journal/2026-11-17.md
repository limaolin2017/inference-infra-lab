## Review — `slot_mapping` (questions first)

Concept note: [Block Table / slot](../concepts/block-table-and-slot-mapping.md).

**Rule:**

~~~text
logical block  = pos // block_size        (quotient: find the block)
physical block = block_table[logical]     (look up the table)
offset         = pos %  block_size        (remainder: find the cell)
slot           = physical × block_size + offset
~~~

- `block_table`: one list per request, logical block → physical block. Used to **read** (attention reads all old K/V).
- `slot_mapping`: one slot number per **new** token in this step. Used to **write** the new K/V into the cache.
- One slot holds one token's K and V. Each layer has its own KV cache; the same token uses the same slot number in every layer.

Case: `block_table = [7, 2, 5]`, `block_size = 4`.

## New — KV cache memory formula (main line item 1)

Concept note: [KV cache memory](../concepts/kv-cache-memory.md).

~~~text
per token   = 2 × layers × KV heads × head_dim × bytes
per request = per token × tokens
~~~

Example model: 32 layers, head_dim 128, FP16 (2 bytes).

| Type | KV heads | Per token | 8K tokens |
| --- | --- | --- | --- |
| MHA | 32 | 512 KiB | 4 GiB |
| GQA | 8 | 128 KiB | 1 GiB |
| MQA | 1 | 16 KiB | 0.125 GiB |

**Corrections:**

- MHA / GQA / MQA differ in the **number of KV heads**, not in blocking. Blocking is PagedAttention memory management.
- KV heads are **projected** with weights, not "split out" of K.

**Where KV cache comes from:**

- Weights hold only **W_K, W_V** (the calculators). K and V are results computed per request.
- At vLLM startup: a profiling run measures memory for weights and activations; **the rest** is reserved as empty KV blocks.
- Why reserve at startup, not per request: (1) GPU allocation is slow and a decode step is only a few ms; (2) avoid fragmentation; (3) the Scheduler needs a fixed total capacity to decide whether to admit new requests. **Not** for warm-up.
